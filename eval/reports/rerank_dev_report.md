## 配置（已冻结）

- base = `hybrid@6`（内容与顺序完全冻结，补充只 append）
- 补充形态 = `N-win`（每锚点 idx-1 与 idx+1）
- 逐题预算 = 0.5 × 该题 base token（原子单元不可拆，放不下整体跳过）
- 排序器 = DeepSeek rerank（仅对补充单元排序，不改 base）
- 锚点数 P=12（补充路径 `supplement_base` 未实现每源上限；每源上限仅存在于窗口路径，未用于本实验）

## 1. 三组公平对比（同 K_base=6 / 同 N-win / 同 0.5×base 预算）

> **下表为旧 cache key 下那一次有效运行的历史结果**（rerank 列依赖旧键缓存命中）。
> 加固 cache key 后**不能用当前 cache-only 复算这些数值**（现为 0/24 命中）。

| 组 | evidence 命中 | ev-MRR | source 命中 | 平均 chunks | 上下文 token（估算） |
|---|---|---|---|---|---|
| hybrid@6（默认基线） | 21/24 | 0.654 | 24/24 | 6.0 | 1163 |
| N-win 补充（无 rerank） | 21/24 | 0.654 | 24/24 | 8.8 | 1704 |
| **DeepSeek rerank + N-win** | **23/24** | **0.666** | 24/24 | 8.9 | 1699 |

> **token 为估算值**：按「字符数 ÷ 4」粗略估计，非真实分词器计数，仅用于相对比较。
> hybrid@6 / N-win 两行不依赖 rerank 缓存；rerank 行依赖旧键缓存的历史 order。

**关键读点**：无 rerank 的 N-win 花了更多 token 却没有任何 evidence 提升（仍 21/24）——
因为确定性排序在 0.5×base 预算内**选错了补充邻居**。加 rerank 后，几乎相同的上下文 token
（1699 ≈ 1704）却把命中提到 23/24。差别**全在「选哪些邻居进预算」**，不在「补多少」。

## 2. 核心指标解读

- **evidence recall：21/24 → 23/24，即 87.5% → 95.8%，提升 8.3 个百分点。**
- **source recall 始终 100%（24/24）**：改善并非发生在「找到正确文档」层面，
  而是发生在**「精确证据片段」层面**——正确文档一直能召回，但含答案的相邻片段此前进不了上下文。
- **最终上下文 token（估算）：1163 → 1699，增加 46.1%**（仍 ≤ 1.5×base 护栏 1745）。
- **ev-MRR：0.654 → 0.666**（不劣于基线）。

> 上述 recall/MRR 均为**检索层 evidence/source 指标**（证据片段是否被检索进上下文），
> **不代表最终生成回答的质量**——本实验未评估答案正确性。

## 4. 逐题净变化与残留失败

| 组 | fixed | broken | 仍失败 |
|---|---|---|---|
| N-win（无 rerank） | 无 | 无 | （无改善） |
| **rerank + N-win** | **dev05, dev20** | **无** | **dev19** |

- **修好 2 题**：`dev05`、`dev20`；**弄坏 0 题**。
- **fixed/broken 是检索层 evidence 指标**（正确证据片段是否进入最终上下文），**不是人工答案质量判断**。
- 「弄坏 0 题」来自 base 完全冻结（不删不重排）带来的**检索 evidence recall 不劣化**——
  该保证**仅限检索层的 evidence/source recall，不延伸到最终回答质量**。
- **dev20 硬门槛**：`path-params.md#2`（含证据的相邻片段）**已进入最终上下文** ✅。
- **仍失败 1 题**：**dev19**（rerank 未能修复；属已知残留难例，不在本轮继续调参范围）。

## 5. 结论

1. **rerank 解决了「预算内无法选中正确邻居」的问题**：证据邻居（如 dev20 的
   `path-params.md#2`）其 anchor 在 base 中名次靠后，纯确定性序会被前排 anchor 的邻居
   挤出 0.5×base 预算；rerank 将证据补充单元提前，使其落入预算。
2. **dev evidence recall 从 21/24 提升到 23/24（87.5%→95.8%，+8.3pp）**，
   source recall 保持 100%，无回归。
3. **代价**：① 额外模型调用（每题约 6894 输入 / 849 输出 token、约 5.28s 延迟）；
   ② 更长上下文（平均 6.0→8.9 chunk，token +46.1%，仍在 1.5×base 护栏内）。

## 6. 产品化建议

- **默认模式 = hybrid@6**：零额外调用、零额外延迟、上下文最短；已达 source 100%、
  evidence 87.5%，满足大多数场景。
- **可选高准确率模式 = rerank + N-win**：在「证据片段必须命中」要求高时开启；
  换取 +8.3pp evidence 命中，代价是每题一次 rerank 调用（约 5.28s、约 7.7k token）
  与约 1.5×上下文。
- **工程护栏（沿用本实验）**：base 冻结（不删不重排，保证**检索 evidence/source recall 不劣化**）、
  逐题 0.5×base token 预算、原子单元不可拆、`allow_api` 硬开关 + cache-only 默认、
  解析失败/异常回退确定性 N-win。
